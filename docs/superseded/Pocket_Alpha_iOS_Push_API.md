# Pocket Alpha — пуши в iOS-приложении

**Спека для iOS-разработчика.** Бэкенд готов и работает на проде с 13.08.2026.
Документ самодостаточный — всё, что нужно для интеграции, здесь.

---

## 1. Как это устроено

У лида, пришедшего из Telegram-бота, пуши уходят в бота — как и раньше.
У лида, зарегистрированного через приложение, Telegram-канала нет, поэтому пуш
**лежит готовым на сервере**: приложение периодически спрашивает «для меня
что-нибудь есть?» и показывает локальное уведомление.

Лид всегда обслуживается **ровно одним** каналом, поэтому один и тот же пуш
физически не может прийти дважды.

Контент пушей общий с телеграм-воронкой: его пишут и включают/выключают на
стороне бэкенда, релиз приложения для этого не нужен.

## 2. Эндпоинты (прод)

Базовый адрес: `https://signals.tradingwithtyler.com`

| Метод | Путь | Зачем |
|---|---|---|
| `GET` | `/userapi/user/{user_id}/push/pending` | забрать готовый пуш |
| `POST` | `/userapi/push/{delivery_id}/clicked` | отметить тап по уведомлению |

### 2.1. Забрать пуш

```http
GET /userapi/user/{user_id}/push/pending?lang=en
Host: signals.tradingwithtyler.com
X-App-Session: <токен сессии>
```

**Параметры пути**

| | |
|---|---|
| `user_id` | наш идентификатор лида — тот самый, который приложение уже получает полем `user_id` в ответе `/pocket/auth/register` и `/pocket/auth/login`. Ничего вычислять и хранить дополнительно не нужно |

**Параметры запроса**

| | |
|---|---|
| `lang` | локаль устройства. `es` → испанский вариант текста, всё остальное → английский. Необязательный |

**Ответ — пуша нет**

```json
{ "has_push": false, "next_poll_after_sec": 900 }
```

**Ответ — пуш есть**

```json
{
  "has_push": true,
  "push": {
    "delivery_id": "fb1266a314944604b3f003803ba63b46",
    "post_id": 20,
    "title": "🧮 Profit Calculation Before The First Deposit",
    "body": "$100 per month turns into …",
    "action": {
      "text": "ENABLE TRADING",
      "url": "https://signals.tradingwithtyler.com?ref=push_post&pid=fb1266a3…&post=20&screen=deposit"
    },
    "lang": "en"
  },
  "next_poll_after_sec": 900
}
```

**Поля**

| Поле | Тип | Что с ним делать |
|---|---|---|
| `has_push` | bool | `false` → ничего не показываем, ждём `next_poll_after_sec` |
| `push.delivery_id` | string (hex) | идентификатор доставки. Нужен для отметки клика |
| `push.post_id` | int | номер поста. Для логов и отладки |
| `push.title` | string | заголовок уведомления. Всегда непустой |
| `push.body` | string | тело уведомления. Всегда непустое, до ~1000 символов — обрезка на стороне iOS |
| `push.action` | object \| **null** | кнопка. **Может быть `null`** — тогда уведомление без действия, тап просто открывает приложение |
| `push.action.text` | string | подпись действия |
| `push.action.url` | string | абсолютный URL. **Ничего к нему дописывать не надо** — вся атрибуция уже внутри |
| `push.lang` | string | на каком языке отдан текст (`en` / `es`) |
| `next_poll_after_sec` | int | через сколько секунд прийти снова. Присылается ВСЕГДА, в том числе вместе с пушем |

**Правила**

- За один ответ приходит **не больше одного пуша**. Если накопилось несколько,
  они разойдутся следующими опросами, по одному, в порядке воронки.
- Между двумя выдачами одному лиду сервер держит паузу (сейчас 30 минут), так
  что частым опросом «вычерпать» очередь нельзя.
- Картинок нет: поле `image_url` не отдаётся. Все уведомления текстовые.
- `next_poll_after_sec` надо уважать — он позволяет менять частоту опроса без
  релиза приложения.
- При `has_push: false` может прийти необязательное поле `reason`
  (`telegram_lead` / `posts_disabled` / `in_app`) — это для отладки, поведение
  приложения от него не зависит.

### 2.2. Отметить клик

```http
POST /userapi/push/{delivery_id}/clicked
Host: signals.tradingwithtyler.com
```

Звать при тапе по уведомлению — до или параллельно с открытием `action.url`.
Идемпотентно, засчитывается первый клик.

Без этого вызова пуш будет числиться доставленным, но непрочитанным, и вся
статистика эффективности по iOS-каналу останется нулевой.

## 3. Авторизация

Ручка отдаёт персональный контент, поэтому закрыта подписанной сессией
приложения:

```
X-App-Session: <токен>
```

Токен приходит полем `session` в ответе `/pocket/auth/register` и
`/pocket/auth/login`, живёт 60 дней.

⚠️ **Сейчас на проде секрет сессий не выставлен**, поэтому проверка работает в
теневом режиме: запросы проходят и без заголовка, недостаток доказательств
только пишется в лог. Для приложения это ничего не меняет — **слать заголовок
надо сразу**, он начнёт требоваться, когда секрет включат, и тогда запросы без
него отобьются.

---

## 4. Что делает приложение

1. **Foreground.** Опрос при каждом выходе приложения на передний план, но не
   чаще, чем разрешает `next_poll_after_sec` (сейчас 15 минут).
2. **Background.** `BGAppRefreshTask` — см. ограничение в §5.
3. **Показ.** Локальное уведомление: `title` → заголовок, `body` → тело.
4. **Тап.** `POST /userapi/push/{delivery_id}/clicked`, затем открыть
   `action.url`, если `action` не `null`.
5. **Смена аккаунта / разлогин.** Сменился `user_id` → ранее полученные и
   непоказанные пуши считаются протухшими, локальные уведомления снимаются.

Дедупликация на клиенте не нужна: сервер отдаёт каждый пуш ровно один раз.

---

## 5. Ограничения и почему так

**Тайминг.** iOS сам решает, когда разбудить приложение в фоне, и у редко
открываемых приложений это единицы раз в сутки. Первые ступени воронки (3, 12,
30 минут после события) в pull-модели приедут «когда система соизволит».

Это принятое ограничение первого шага, а не недосмотр. Целевая схема — APNs с
device-токенами. Серверный отбор пуша при переходе на APNs переиспользуется как
есть, меняется только транспорт, поэтому **контракт из §2 переживёт переход** —
интеграцию не придётся переписывать.

**Выдача = доставка.** Пуш помечается доставленным в момент ответа, до показа.
Если приложение убьют между ответом и показом — пуш потерян. Размен
сознательный: дубль читается как спам и стоит отписки, пропуск — нет.

**Без картинок.** Картинки постов хранятся как идентификаторы файлов внутри
Telegram и по HTTPS недоступны. Добавятся вторым шагом — появится
необязательное поле `image_url`, контракт при этом не меняется.

## 6. Идентификатор лида

`user_id` приложение получает от сервера при регистрации и при логине —
вычислять его на клиенте не нужно и нельзя.

**Кросс-девайс работает.** Логин с другого устройства ищет лида по его аккаунту
Pocket и возвращает **тот же** `user_id`. Новый профиль не заводится — проверено
на живой базе, включая лидов, заведённых по старой схеме идентификаторов.

Нативной оболочке `user_id` надо получить из веб-слоя (он лежит в
`localStorage` под ключом `tw-app-user-id`) либо выполнять логин нативно —
что удобнее на вашей стороне.

## 7. Как проверить, что живо

```bash
# 1. Пуш отдаётся
curl -s -H "X-App-Session: <токен>" \
  "https://signals.tradingwithtyler.com/userapi/user/<user_id>/push/pending?lang=en"

# 2. Дубля нет — повторить тот же запрос сразу
#    → {"has_push":false,...}

# 3. Клик доехал
curl -s -X POST \
  "https://signals.tradingwithtyler.com/userapi/push/<delivery_id>/clicked"
#    → {"ok":true,"updated":true,...}
```

---

## 8. Что уже проверено на стороне бэкенда

| Проверка | Результат |
|---|---|
| Лид, которому подошёл пост | отдан корректный `title` / `body` / `action.url` |
| Повторный опрос сразу | `has_push: false` — сработала пауза между выдачами |
| Следующий пост по расписанию | приехал в свой срок, порядок воронки сохранён |
| Пост, у которого в телеграме картинка | отдан текстом |
| Телеграм-лид | `has_push: false`, `reason: telegram_lead` |
| Отметка клика | проставляется, повтор — без эффекта |
| Кросс-девайс | тот же `user_id`, новый профиль не заводится |
| Телеграм-канал | не затронут |

Единственное, что не проверено живым прогоном, — полёт нашего идентификатора до
Pocket и обратно в постбэке: для этого нужна реальная регистрация на брокере.
